2. **RFC 9849 §6.1.3 Padding Invariant:** Empirical proof that Google Chrome pads outer ClientHello ciphertexts strictly in **32-byte buckets** ($L_{\text{payload}} \pmod{32} \equiv 16$).
3. **JA4 Resiliency over JA3:** Demonstration that JA4 remains deterministic (`t13d1517h2_8daaf6152771_cb7bf5808d99`) under Chrome's aggressive extension shuffling, whereas JA3 hashes fragment across every connection.
4. **Coexistence of ECH with Post-Quantum Hybrid TLS:** Simultaneous deployment of ECH (`0xfe0d`) and X25519MLKEM768 (`0x11ec`, RFC 10024) in the wild.

## 4. Empirical Mathematical Verification of Padding Invariant

RFC 9849 §6.1.3 establishes the following recommendation for preventing length-based traffic analysis:
$$\text{Length}(\text{EncodedClientHelloInner}) \equiv 0 \pmod{32}$$

Because an AEAD cipher (such as AES-128-GCM) appends a fixed 16-byte authentication tag ($L_{\text{tag}} = 16$), the resulting outer wire ciphertext length must satisfy:
$$L_{\text{payload}} = \text{Length}(\text{EncodedClientHelloInner}) + 16 \implies L_{\text{payload}} \pmod{32} \equiv 16$$

## 5. Fingerprint Invariance: JA3 Fragility vs JA4 Robustness

*Conclusion on JA3:* Because JA3 concatenates extensions in the raw wire order, extension permutation completely breaks fingerprint tracking.

  - Database Identification: **`[Chromium (browser)]`**

*Conclusion on JA4:* By sorting cipher suites and extensions alphabetically prior to hashing, JA4 achieves 100% deterministic identification across every randomized ECH flow.
