  JA4S, in all three implementations. Server extensions are now hashed in the
  order the server sent them, with ALPN and GREASE kept, which is what FoxIO's

    gave i.

    codes are added.

  into the JA3S calculation itself. Across 74 pcaps, about 10,300 JA3 and JA3S
  values are identical before and after, and no flows were gained or lost.

● No worries. This is the idea everything else rests on, so here it is from the
  beginning.

  What "spoofing" means here

  Every program that opens an HTTPS connection leaves fingerprints, and our
  engine reads them. In this project, "spoofing" means a program making itself
  look like a different program: for example, a scraping bot or a piece of
  malware disguising itself as Safari on a Mac, so that websites and security
  tools trust it.

  The disguise is cheap, because the main fingerprint we use is easy to fake.

  The two layers of every connection

  When a client connects, two different pieces of software write two different
  packets:

  ┌────────────────┬──────────────────┬──────────┬─────────────────────────┐
  │     Packet     │    Written by    │ What we  │ Can the program change  │
  │                │                  │ compute  │           it?           │
  ├────────────────┼──────────────────┼──────────┼─────────────────────────┤
  │ ClientHello    │ The application  │ JA3 /    │ Yes, easily. Tools like │
  │ (the TLS       │ (Chrome, curl, a │ JA4      │  curl-impersonate copy  │
  │ handshake)     │  bot)            │          │ Chrome's exactly.       │
  ├────────────────┼──────────────────┼──────────┼─────────────────────────┤
  │ SYN (the TCP   │ The operating    │ JA4T,    │ Not easily. It needs    │
  │ connection     │ system (Windows, │ plus the │ administrator rights    │
  │ request)       │  Linux, macOS)   │  TTL     │ and raw packet          │
  │                │                  │          │ crafting.               │
  └────────────────┴──────────────────┴──────────┴─────────────────────────┘

  A bot can say it's Safari in its ClientHello, but it can't easily change the
  fact that its SYN was built by, say, Linux.

  Detecting spoofing means checking whether the two stories agree

  A shop analogy fits. Someone hands you a credit card that says "John Smith,
  Gold Member, UK resident" (the ClientHello), but they're paying from a phone
  with a Brazilian SIM (the SYN). Neither fact is suspicious on its own; the
  contradiction is. We never prove someone is lying. We notice that their claims
  can't all be true at once.

  Why the catalog is needed

  The ClientHello by itself is just a hash, such as t13d1715h2_5b57614c22b0_….
  That hash doesn't say "I am Safari, I only run on macOS". Something has to
  translate the hash into a claim, and that's the catalog's job: it's a lookup
  table from fingerprint to known identity.

  fingerprint  t13d2014h2_…  →  "Safari"   expected_os: macos

  So the check runs in three steps:
  1. What does the TLS say? Look up the JA4/JA3 in the catalog: Safari, which
     only runs on macOS.
  2. What does the TCP say? Read the SYN: its option layout and TTL point to
     Linux.
  3. Compare: macOS ≠ Linux, so IMPERSONATION_MISMATCH.

  Without step 1 there is no claim, and nothing to contradict.

  Why only some catalog entries have expected_os: Chrome, Firefox and curl run
  on every OS, so a Chrome fingerprint coming from Linux is perfectly normal.
  Only clients that are tied to one OS make a checkable claim: Safari to
  macOS/iOS, and built-in Windows components to Windows. Your main catalog
  contains none of these yet, which is why the lab ships its own small catalog.
  That file says "this test client only exists on Windows", so we can then send
  it from Linux, macOS or FreeBSD SYNs and watch the engine catch the lie.

  The three alerts, each a different kind of contradiction

  1. IMPERSONATION_MISMATCH: the TLS and TCP layers disagree. "My TLS says a
     Windows-only client, my SYN says Linux." This is the bot in disguise. It
     needs the catalog.
  2. STACK_ANOMALY: the SYN disagrees with itself. The TCP options say Windows
     but the TTL says Linux, or the options are malformed. A real kernel never
     produces that combination, so someone crafted the packet by hand to look
     like another OS and didn't get it quite right. No catalog needed.
  3. TTL_MISMATCH: the packets of one connection disagree. The SYN arrived after
     8 hops but the ClientHello after 81. They came from different machines, so
     something injected a packet into someone else's connection. No catalog
     needed.

  What it can't catch

  - A perfect spoof. An attacker who copies the TLS and every SYN detail and the
    TTL can't be told apart. That's scenario 50016 in the lab, and we include
    it to show the limit honestly.
  - A disguise that matches the attacker's real OS. Chrome on Linux is something
    real people use, so curl-impersonate on Linux posing as Chrome produces
    nothing to contradict.

  So the system doesn't make spoofing impossible. It forces an attacker to fake
  two independent layers consistently instead of one, which is much harder.

  How this maps onto the lab

  Each connection in ja4t_lab.pcap is one deliberately constructed lie, or one
  honest client to check we don't raise false alarms. The catalog provides the
  claim. The engine's job is to raise exactly the right alert for each
  connection, and the script checks that it does.
