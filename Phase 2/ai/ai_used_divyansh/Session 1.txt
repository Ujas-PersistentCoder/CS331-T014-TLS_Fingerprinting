  What the project is

  The repo has three implementations. Only one matters now:

  - code/python and code/cpp are Phase 1 (the midterm). They read captured
    traffic and compute JA3/JA4 fingerprints of the TLS handshake.
  - Phase 2/engine is the C++ rewrite your team is building now. Phase
    2/Phase2_team_share.md splits the remaining work into three tracks, and
    Track A is "JA4T & Cross-Layer Impersonation Detection". So JA4T was already
    planned; nobody had started it (the JA4T branch was identical to main).

  What JA4T is

  A connection happens in two stages, and each is built by a different part of
  the computer:

  1. The TCP handshake (the "SYN" packet). The operating system builds this. It
     contains settings like the receive window size, a list of TCP options in a
     fixed order, the maximum segment size (MSS), and the IP TTL. Every OS has
     its own defaults: Linux and macOS start the TTL at 64, Windows at 128, and
     each orders the options differently.
  2. The TLS ClientHello. The application builds this. JA3/JA4 fingerprint it.

  JA4T fingerprints step 1. The format is <window>_<options>_<MSS>_<window
  scale>. Your own pcaps contain all three common stacks:

  ┌────────────┬────────────────────────────────┬─────────────────────────┐
  │   Stack    │              JA4T              │         Seen in         │
  ├────────────┼────────────────────────────────┼─────────────────────────┤
  │ Windows 11 │ 64240_2-1-3-1-1-4_1460_8       │ test_new.pcap (layout)  │
  ├────────────┼────────────────────────────────┼─────────────────────────┤
  │ Linux      │ 64240_2-4-8-1-3_1460_7         │ the client_*.pcap files │
  ├────────────┼────────────────────────────────┼─────────────────────────┤
  │ macOS      │ 65535_2-1-3-1-1-8-4-0-0_1460_6 │ chrome.pcap             │
  └────────────┴────────────────────────────────┴─────────────────────────┘

  How it relates to "spoofing"

  A program can easily copy another client's ClientHello. curl-impersonate sends
  Chrome's exact one, so JA4 alone can't tell them apart. Changing the SYN is
  harder, because the kernel builds it. So if the TLS says "I'm a Windows-only
  client" but the SYN says "Linux kernel", something is lying.

  Strictly, the TCP options are layer 4 and the TTL is layer 3. The engine now
  runs three checks:

  - IMPERSONATION_MISMATCH: the TLS fingerprint implies one OS, the SYN shows
    another.
  - TTL_MISMATCH: the SYN and the ClientHello on the same connection arrive with
    different TTLs. That suggests a packet was injected from a different host.
    This is the closest thing to classic network-layer spoofing detection.
  - STACK_ANOMALY: the SYN's option layout says one OS but its TTL says another.
    That suggests a hand-crafted SYN.

  The engine also prints a JA4TS line for the server's reply (SYN-ACK).

  Two decisions you should know about

  1. The impersonation check uses a new catalog field, expected_os, not the
  existing os. Running on real data showed why. chrome.pcap matches the
  catalog's "Chromium (os: linux)" entry, but its SYN is clearly macOS. Chrome
  uses the same TLS code on every OS, so os only records where something was
  captured. Comparing against it would flag real Chrome on a Mac as an attack.
  expected_os is opt-in: set it only for TLS stacks that exist on one OS, such
  as Windows SChannel or Apple's Safari stack.

  The honest consequence for your report: curl-impersonate on Linux pretending
  to be Chrome is undetectable this way, because real Chrome on Linux looks
  identical. It is detectable when the impersonated client can't run on the
  attacker's OS, e.g. a Safari or SChannel claim coming from a Linux machine.

  2. STACK_ANOMALY only checks client SYNs. On server replies it fired 20 times
  in your pcaps, all from CDNs (Cloudflare/Google style) that run Linux with a
  tuned TTL of 128 or 255. That's normal for servers, so it would only be noise
  there. After this change, your real captures raise 0 alerts.

  What changed

  - New module: ja4t.cpp (Phase%202/engine/src/ja4t.cpp) and ja4t.hpp
    (Phase%202/engine/include/tlsfp/ja4t.hpp) parse the SYN, compute the
    fingerprint, and guess the OS.
  - Engine: capture.cpp (Phase%202/engine/src/capture.cpp) remembers each SYN
    until its ClientHello arrives (memory is capped at 64K connections), prints
    JA4T/JA4TS, and runs the checks.
  - Catalog: db.cpp (Phase%202/engine/src/db.cpp) accepts ja4t/ja4ts sections
    and expected_os. The Python GUI reads the same Redis records and ignores the
    extra field.
  - CLI: -c <catalog.json> loads an extra catalog; the run summary now counts
    SYNs and alerts.
  - Tests: test_ja4t.cpp (Phase%202/engine/tests/test_ja4t.cpp) has 23 unit
    tests (run with ctest), including FoxIO's own reference values.
  - Lab: ja4t_lab.py (Phase%202/testbed/ja4t_lab.py) generates a pcap with one
    connection per scenario and checks the engine's verdict on each. All 5 pass.
  - Team notes: JA4T.md (Phase%202/engine/JA4T.md) covers the format, the
    checks, and the limits.
  - Unrelated fix: in CMakeLists.txt (Phase%202/engine/CMakeLists.txt), the
    Debug build never linked before (the sanitizer link flag was PRIVATE instead
    of PUBLIC).

  Things to know

  - Running the lab with -c wrote one test record into your local Redis
    (tlsfp:ja3:3d7dae6f21f71b9e304c282ad06509f8). It's harmless; delete it with
    redis-cli DEL on that key if you like.
  - The lab's generated files in Phase 2/testbed/generated/ are untracked.
    Commit them or add them to .gitignore, your call.
